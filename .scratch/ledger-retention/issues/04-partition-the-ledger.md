# Convert ledger to PARTITION BY RANGE (ts_at)

Status: ready-for-agent
Type: task
Created: 2026-08-11

PRD: [`../PRD.md`](../PRD.md) · Depends on: 03 · Unblocks: 05

> **Highest-risk issue in the epic.** It rewrites the whole ledger table, and migrations run inside
> `Open()` — so this executes when the new bot binary first starts, unattended, under launchd. At
> 17k rows it is milliseconds, but treat the deploy as a cutover: stop the bot, `mise run db:backup`,
> `mise run db:migrate`, verify, start.

## Spike first

Three things could not be verified from documentation. Each is a few lines in a scratch database and
all three gate the migration's shape:

1. `GENERATED BY DEFAULT AS IDENTITY` + `PRIMARY KEY (id, ts_at)` + `PARTITION BY RANGE (ts_at)`
   accepted together.
2. `pg_get_serial_sequence('ledger','id')` returns non-NULL on the partitioned parent. Both
   `cmd/store-migrate/copy.go` and `verify.go` depend on it; a NULL breaks cutover *and* rollback.
3. Whether a partial `UNIQUE` index is legal on a partitioned parent — moot after issue 03, but
   confirm rather than assume, since the migration drops the index either way.

Record the answers in this file under `## Comments` before writing the migration.

## Decisions

- **`ts_at TIMESTAMPTZ NOT NULL`, written explicitly by every INSERT.** `ts` stays `BIGINT` unix
  seconds; the ADR records why the three tidier alternatives (stored generated column, expression
  key, `BEFORE INSERT` trigger) are each independently illegal on PG 18.4. The trigger one is the
  dangerous near-miss: it would have passed in tests and failed in production.
- **No `DEFAULT` on `ts_at`.** A forgotten insert path must fail loudly on its first row rather than
  silently mis-bucket history into whatever `now()` happened to be.
- **Nothing enforces `ts_at = to_timestamp(ts)`** — it cannot, given the above. The invariant lives
  in a comment at each INSERT site and in a test that checks every row.
- **PK becomes `(id, ts_at)`.** A partitioned table's PK must include all partitioning columns. This
  weakens "id is globally unique" to "(id, ts_at) is unique", which is academic — ids come from one
  sequence — and invisible to Go.
- **The migration creates the back-dated children itself.** gopartman's provisioner builds
  `{current} ∪ {premake futures} ∪ {default}` and **never** creates a partition in the past;
  `PartitionData` records a `DrainAnomaly` rather than creating a missing child. Rows stranded in
  the default partition can never expire, because `ListExpiredPartitions` only considers registered
  bounded partitions. "Let the library sort it out" does not work.
- **Names must match gopartman's grammar exactly** — `{parent}_{YYYYMMDD}`, UTC, month/day start.
  `ImportExisting` silently `Skip`s non-conforming names, and a silently skipped partition is one
  that never expires. The default must be exactly `ledger_default`: `drain.PartitionData` hardcodes
  `TableName + "_default"`, and `RegisterParent` would otherwise try to create a second `DEFAULT`
  partition and fail.
- **SQLite is a documented no-op**, so `wantSchemaVersion` stays equal across dialects — the migrate
  tool prints them side by side.
- **The Down migration gets written and tested.** A down migration nobody ran is a rollback plan
  nobody has.

## Work breakdown

1. **`store/postgres/migrations/00005_partition_ledger.sql`** — goose wraps it in one transaction by
   default; keep that, there is no `CONCURRENTLY` anywhere.

   ```sql
   -- +goose Up
   CREATE TABLE ledger_new (
       id BIGINT GENERATED BY DEFAULT AS IDENTITY, user_id TEXT NOT NULL,
       delta BIGINT NOT NULL, reason TEXT NOT NULL, ref TEXT,
       ts BIGINT NOT NULL, ts_at TIMESTAMPTZ NOT NULL,
       PRIMARY KEY (id, ts_at)
   ) PARTITION BY RANGE (ts_at);

   CREATE TABLE ledger_default PARTITION OF ledger_new DEFAULT;

   DO $$
   DECLARE d date;
   BEGIN
     FOR d IN
       SELECT generate_series(
                COALESCE((SELECT (to_timestamp(MIN(ts)) AT TIME ZONE 'UTC')::date FROM ledger),
                         (now() AT TIME ZONE 'UTC')::date),
                (now() AT TIME ZONE 'UTC')::date, interval '1 day')::date
     LOOP
       EXECUTE format(
         'CREATE TABLE IF NOT EXISTS %I PARTITION OF ledger_new FOR VALUES FROM (%L) TO (%L)',
         'ledger_' || to_char(d, 'YYYYMMDD'), d::timestamptz, (d + 1)::timestamptz);
     END LOOP;
   END $$;

   INSERT INTO ledger_new (id, user_id, delta, reason, ref, ts, ts_at)
   SELECT id, user_id, delta, reason, ref, ts, to_timestamp(ts) FROM ledger;

   DROP TABLE ledger;
   ALTER TABLE ledger_new RENAME TO ledger;
   CREATE INDEX ledger_user ON ledger(user_id);

   SELECT setval(pg_get_serial_sequence('ledger', 'id'),
                 COALESCE((SELECT MAX(id) FROM ledger), 0) + 1, false);
   ```

   Watch the `date`/`timestamptz` boundary: partition bounds are `timestamptz`, so `d::timestamptz`
   is interpreted in the server's `TimeZone`. Set `SET LOCAL TimeZone = 'UTC'` at the top of the
   migration so the bounds line up with the UTC-derived names, or the children are silently offset
   by the server's zone.

2. **`store/sqlite/migrations/00005_partition_ledger.sql`** — a no-op with a comment: SQLite has no
   partitions and no retention (see the PRD's Out of scope), and the file exists so the two dialects
   stay on the same version number.

3. **`store/postgres/points.go`** — `ts_at` on all six INSERT sites (`Credit` ×2, `Grant`, `Spend`,
   `Transfer` ×2), each as `to_timestamp($n)` re-using the `ts` argument, with a one-line comment at
   the first: `ts_at is ts in timestamp form; nothing enforces it, so it is written here or the row
   lands in the wrong partition`.

4. **`cmd/store-migrate/copy.go`** — the copier's ledger row gains a Postgres-only derived column,
   following the `game_rounds.state::jsonb` precedent in `insertStatement`: for a Postgres
   destination the `ledger` INSERT names 7 columns and binds the 7th as `to_timestamp($n)` re-using
   the `ts` argument. SQLite's `ledger` never has `ts_at`.

5. **`store/postgres/migrate_test.go`** — `wantSchemaVersion` → 5 (and SQLite's), pass `ts_at` in
   `TestLedgerIdentityAcceptsExplicitIDs`.

## Tests

- **`TestLedgerIsPartitionedByRange`** — `relkind='p'` and `partstrat='r'` on `ledger`.
- **`TestLedgerDefaultPartitionExists`** — asserts the exact name `ledger_default`. gopartman
  hardcodes it; a rename here is a failure two issues later.
- **`TestEveryLedgerRowHasTsAtMatchingTs`** — `SELECT count(*) FROM ledger WHERE ts_at <> to_timestamp(ts)`
  is 0, run after the conformance workload so it covers all six INSERT sites.
- **`TestPartitionBoundsAreUTC`** — a row with a `ts` late in a UTC day lands in that day's child,
  not the next one. This is the migration's most likely silent bug.
- **`TestLedgerIdentityAcceptsExplicitIDs`** still passes — the explicit-id path is how
  `cmd/store-migrate` works in both directions.
- **Down migration**: apply Up then Down on a seeded fixture, assert `ledger` is a plain table with
  every row and the sequence intact.
- **Round trip**: `cmd/store-migrate` pg → sqlite → pg with `verify` passing.

## Acceptance

- `mise run test:all` green.
- Against a restored production copy: `\d+ ledger` shows `Partition key: RANGE (ts_at)` and ~28
  children plus `ledger_default`; `SELECT count(*) FROM ledger` is 17,315; `ledger_default` is
  empty; `SELECT pg_get_serial_sequence('ledger','id')` is non-NULL.
- The bot starts, `!marks` and `!give` work, and the new rows land in today's child (not the
  default).
